## Group 1 — bytes / value types

### RX-L0-01 · Fixed-width opaque value types at the primitives level (`Address`/`Hash`/`Bytes32`/`UInt256`) · Tier B · owner-layer L0
- **Plan claim / disposition:** §2 DEFAULT — "opaque types over `Array[Byte]`/`ByteString`, type-distinct" at `bytes` L0, not pushed up into `domain`; §5 idiom target (opaque erase the wrapper, zero-cost).
- **fukuii AS-IS:** value types lived in `domain`; `bytes/` exposed only raw `ByteString`/`Array[Byte]` (§6 gap).
- **Reference source (byte-cited):**
  - go-ethereum `common/types.go` — `type Hash [32]byte`, `type Address [20]byte` (fixed-width named arrays); `SetBytes` right-aligns.
  - besu `datatypes` (Tuweni `BytesHolder`/`Bytes32`) — the JVM-implementation lens; wrapper over a backing byte holder.
  - reth alloy `B256`/`Address`/`U256` (cross-check) — newtype wrappers.
  - Built: `bytes/Hash.scala:13` `opaque type Hash = ByteString`, `UInt256.scala:19` `opaque type UInt256 = BigInt`, `Hash.scala:65` `type Bytes32 = Hash`.
- **Q1 appropriate?** Yes — unanimous across the field; type-distinctness (`Hash` ≠ `Address`) is the point and opaque types deliver it at zero runtime cost.
- **Q2 what to implement?** Yes — opaque wrapper is the correct Scala-3 realization; the JVM caveat (erase the wrapper, not the 32-byte backing array) is honored and the nethermind inline-struct route correctly rejected (RX-L0-04).
- **Q3 mechanism + blast radius?** Correct. Blast radius: every layer L1+ imports these as the currency types; `Hash.apply` is **strict** (exactly 32 bytes, fail-loud) with a separate `fromBytesTruncating` mirroring geth `SetBytes` — the strict/lenient split is the right seam so parse-sites opt into leniency explicitly. Plan states it.
- **Verdict:** CONFIRMS.

### RX-L0-02 · `UInt256` 256-bit modular arithmetic byte-exact to `holiman/uint256` · Tier A (R4 byte-exact) · owner-layer L0
- **Plan claim / disposition:** §7 DEFAULT(floor) — 256-bit modular arithmetic belongs at `bytes` (L0), byte-exact to holiman/uint256: `Div`/`Mod` by zero → 0, `Exp(x,0)=1` incl `0^0=1`; EVM-gas-metered semantics (EXP gas, SIGNEXTEND, signed SDIV/SMOD/SAR) deferred to `evm` L3.
- **fukuii AS-IS:** arithmetic was carried up in `domain`; §7 moves it down.
- **Reference source (byte-cited):**
  - go-ethereum `holiman/uint256` — `Div`/`Mod` return 0 on zero divisor; `Exp(x,0)=1`. Canonical form is 32-byte big-endian left-zero-padded.
  - Built: `UInt256.scala:87` `def /(y) = if (y==0) Zero else x/y`; `:90` `mod(y) = if (y==0) Zero else x.mod(y)`; `:93` `pow(y) = x.modPow(y, Modulus)` (so `x^0=1`); `:59` `wrap(n) = n.mod(Modulus)` (BigInt.mod is non-negative → correct two's-complement wrap for underflow); `:105` `unary_~ = MaxValue ^ x`; `:108-113` shift saturate to Zero at ≥256.
- **Q1 appropriate?** Yes — arithmetic on the number type is universal (holiman, Tuweni `UInt256`); placing it at L0 is the correct floor.
- **Q2 what to implement?** Yes — the zero-divisor→0 and `0^0=1` conventions are EVM-consensus semantics matched exactly; the deliberate exclusion of gas-metered opcode semantics to L3 is the correct layer boundary.
- **Q3 mechanism + blast radius?** Correct. `apply(BigInt)` **rejects** out-of-range input (`require(n>=0 && n<Modulus)`) rather than silently reducing — right for a constructor with no wrapping justification, whereas the arithmetic ops wrap. Blast radius: L3 EVM word semantics build on this; the L3 gas-metered layer must *not* re-implement modular arithmetic, only meter it. Plan states the boundary (§ Layer boundaries).
- **Verdict:** CONFIRMS. forge/beacon co-sign at build (word arithmetic is state-affecting).

### RX-L0-07 · JVM-integer RLP-offset overflow (J-RLP-1/2/3, `Int`→`Long`) · Tier A (R4) · owner-layer L0
- **Plan claim / disposition:** §9 — J-RLP-1 (`Int`→`Long` offset overflow, invisible to a Go comparison, caught only by the besu JVM lens) remediated; the besu `Math.toIntExact` / `extractSizeFromLongItem` gate.
- **fukuii AS-IS:** an `Int` length read could wrap negative on a 4-byte length with the high bit set, or overflow the payload-end range-check.
- **Reference source (byte-cited):**
  - go-ethereum `rlp/raw.go:387-416` `readSize` reads slen **1..8** into a `uint64` (Go has no 31-bit array-index ceiling) — so geth's own code cannot exhibit J-RLP-1; the bug is a **JVM-only expression** (the besu lens rationale).
  - besu `RLPDecodingHelpers.extractSizeFromLongItem` — reads the length then `Math.toIntExact` gates it against `Int` before indexing.
  - Built: `RLP.scala:126-132` `bigEndianLengthToLong` carries the length as `Long`; `:169/198` reject `lengthOfLength > MaxLengthOfLength (=Integer.BYTES=4)`; `:183/210` compute `end = beginPos.toLong + length - 1` in `Long` so the `end >= data.length` guard cannot wrap.
- **Q1 appropriate?** Yes — this is a correctness fix specific to our stack; a Go-authority-only read would have missed it (it did, historically).
- **Q2 what to implement?** Yes — carrying length in `Long` + a `MaxLengthOfLength=4` cap is the right JVM realization.
- **Q3 mechanism + blast radius?** Correct. **SHARPENS-worthy note:** fukuii's 4-byte length-of-length cap is **stricter** than geth's 8-byte `readSize`, but behaviorally equivalent on every buffer-realizable input — no `Array[Byte]` can hold ≥2³¹ bytes, so a 5–8-byte length declares a payload no real buffer can satisfy, which geth *also* rejects via `ErrValueTooLarge` (contentsize > len(buf)). So the cap never rejects a valid mainnet item; it rejects adversarial oversize headers earlier. The built code documents this (`RLP.scala:28-32`) — fold the "stricter-but-equivalent, never rejects a realizable item" rationale into the plan §9 J-RLP note so a future reader doesn't "fix" the cap up to 8 to "match geth."
- **Verdict:** SHARPENS. **Plan edit:** §9 — record that the 4-byte length-of-length cap is a deliberate JVM-index tightening, behaviorally equivalent to geth on all buffer-realizable inputs (do not widen to 8).

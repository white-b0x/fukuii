## Group A — account / state value types

### RX-L1-01 · `Account` state value type + RLP · Tier A · owner-layer L1
- **Plan claim / disposition:** `Account(nonce, balance, storageRoot, codeHash)`; straight-field type,
  `derives RLPCodec` (§1 table, §5). DEFAULT shape; byte-exact vs geth `state_account.go`.
- **fukuii AS-IS:** old `domain.Account` present; lived in the SCC `domain` package that imported up.
- **Reference source (byte-cited):**
  - go-ethereum `core/types/state_account.go:31-35` — `type StateAccount struct { Nonce uint64; Balance
    *uint256.Int; Root common.Hash; CodeHash []byte }`. **Field order Nonce→Balance→Root→CodeHash is the
    RLP order.** Note **`Balance` is `*uint256.Int`, not `*big.Int`** (geth migrated the state balance to
    uint256).
  - besu `datatypes/AccountValue.java` — `getNonce`/`getBalance`/`getStorageRoot`/`getCodeHash` (JVM lens;
    the same 4 fields).
  - core-geth `core/types/state_account.go` — identical struct (shared; inherit).
- **Q1 appropriate decision?** Yes. A 4-field immutable value with `derives RLPCodec` is exactly geth's
  `StateAccount`; nothing network-specific.
- **Q2 what we should implement?** Yes. No better alternative; every client models the same 4 fields.
- **Q3 understanding + blast radius correct?** Mechanism: yes. **Blast radius SHARPEN:** `Account.balance`
  must be the L0 `UInt256` opaque (geth uses `uint256.Int`, not arbitrary big-int) — the state-account RLP
  and the state-trie leaf hash depend on the 32-byte width. Every L2 trie leaf, L3 EVM `BALANCE`, and L4
  state-transition reads this type; the plan says "balance" without pinning it to L0 `UInt256`. Blast
  radius spans L2/L3/L4 (state-root-affecting).
- **Q4 correction:** none needed beyond the sharpen.
- **Verdict:** SHARPENS
- **Plan edit:** §1 Account row — annotate `balance: Wei`/`UInt256` (L0 32-byte), not a bare `BigInt`; add
  to §8 DoD the `Account` RLP round-trip must assert `Balance` encodes as a 32-byte-bounded quantity vs
  geth `state_account.go` (already listed as a reference vector — pin the width).

## Group B — block / header

### RX-L1-04 · Fork-variant `BlockHeader` + trailing-optional RLP omission · Tier A · owner-layer L1
- **Plan claim / disposition:** hand-written `given RLPCodec[BlockHeader]` with
  `DerivationPolicy(omitTrailingOptionals)`; geth `rlp:"optional"` contract — present-from-a-fork,
  omitted-before, **once present all later must be present**; network-prefixed positive-keyed per-fork
  layout, NOT `else-means-ETC` fallthrough (§5, §7, §9). Tests enumerate per-fork field **count**: ETH
  legacy(15)→London(+baseFee)→Shanghai(+withdrawalsRoot)→Cancun(+blobGasUsed,+excessBlobGas,
  +parentBeaconRoot)→Prague(+requestsHash); ETC pre-Olympia = **none** of these. Tier-A, forge+beacon gate.
- **fukuii AS-IS:** fork-variant header via ad-hoc extra-fields coupling (ECIP-1097 `Hef*`); risk of an
  `Eth*` field on an `Etc*` header (§6 gap).
- **Reference source (byte-cited):**
  - go-ethereum `core/types/block.go:68-108` — `type Header struct` fixed 15-field prefix
    (`ParentHash, UncleHash, Coinbase, Root, TxHash, ReceiptHash, Bloom, Difficulty, Number, GasLimit,
    GasUsed, Time, Extra, MixDigest, Nonce`), then the trailing-optionals **in this exact order**:
    `BaseFee` (EIP-1559, :86), `WithdrawalsHash` (EIP-4895, :89), `BlobGasUsed` (EIP-4844, :92),
    `ExcessBlobGas` (EIP-4844, :95), `ParentBeaconRoot` (EIP-4788, :98), `RequestsHash` (EIP-7685, :101),
    **`BlockAccessListHash` (EIP-7928, :104)**, **`SlotNumber` (EIP-7843, :107)** — all `rlp:"optional"`.
  - besu `ethereum/core/.../BlockHeader.java` + `BlockHeaderBuilder.java` (JVM staged construction lens).
  - core-geth `core/types/block.go` — ETC header carries **none** of the base-fee/withdrawals/blob trailing
    fields pre-Olympia (its `Header` predates them); ETC extra-data / ECIP-1097 fields are ETC-frozen.
- **Q1 appropriate decision?** Yes. Hand-written codec + positive-keyed per-fork layout is correct; the
  trailing-optional omission byte-contract is geth's and is consensus.
- **Q2 what we should implement?** Yes. No alternative — the omission rule is a spec invariant.
- **Q3 understanding + blast radius correct?** Mechanism: yes. **Blast-radius / mechanism SHARPEN — the
  plan's field-count enumeration is stale and treats the tail as closed at Prague.** Current geth has **8**
  trailing-optionals (through `BlockAccessListHash` and `SlotNumber`), not the 6 the plan lists. The tail
  is **open-ended** (Osaka+ ETH forks keep appending). fukuii's header codec must be built for a growing
  tail, and the DoD test must be structured as "assert the exact tail present at fork F" for **each** fork
  including the two new ones — not a hardcoded stop at `requestsHash`. These two are ETH-family (beacon
  owns them); ETC stays at zero trailing fields. This also ripples to L6 ForkId (per-fork header shape) and
  L2 header storage.
- **Q4 correction:** extend the §7 per-fork test list: ETH …→Prague(+requestsHash)→**Osaka+(
  +blockAccessListHash EIP-7928, +slotNumber EIP-7843)**, marked "tail is open — new ETH forks append;
  the codec must not assume a fixed max field count." Keep the "mid-run gap rejected" invariant.
- **Verdict:** SHARPENS
- **Plan edit:** §7 "RLP trailing-optional-omission policy" test block — add the two current geth fields and
  the "open tail" note; §9 "fork-variant BlockHeader trap" — note the tail grows with each ETH fork (beacon
  gate), ETC stays at zero.

    bytes map to their type; `:124` `transactionTypeByOpaqueByte(opaqueByte)` returns `Optional` —

    plan cites.
  - go-ethereum `core/types/transaction.go:207-213` — `decodeTyped` switch on `AccessListTxType/

  invariant is consensus (a silently-legacy-decoded typed tx = wrong tx hash). Plan states it in §7 test.
- **Verdict:** CONFIRMS

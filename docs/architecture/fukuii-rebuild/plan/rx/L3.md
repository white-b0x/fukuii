**Four-questions format (operator directive).** Every entry answers, before its verdict:
- **Q1 — appropriate decision?** is the plan's disposition (DEFAULT/STRUCTURAL/OPTIONAL/OBSOLETE/OPEN) the right call given the source?
- **Q2 — right thing to build?** the right thing vs. a better alternative the multi-client read reveals vs. NOTHING (YAGNI / seam suffices)?

Verdict: **CONFIRMS** (all yes) / **CORRECTS** (Q1/Q2/Q3 no → Q4 fix, plan edit required) / **SHARPENS** (right decision, Q3 reveals a load-bearing detail/blast-radius edge to fold in).

## Group A — opcode set / interpreter loop

### RX-L3-01 · Immutable `ProgramState` `@tailrec` interpreter loop · Tier A · owner-layer L3
- **Plan claim / disposition:** §6 + optimizations L3 — **OPEN (benchmark-gated).** The AS-IS immutable `@tailrec` loop (`copy`-per-opcode, fresh `Stack`/`Memory`) is the one pure-functional loop among the seven; `mutable-state-parity.md` calls it a divergence + measurable regression, but it trivially satisfies R2 (no shared mutable frame across instances). Decide by an alloc/throughput bench, not inertia; correctness-neutral (byte-identical to a mutable frame), so it does **not** gate the consensus DoD.
- **fukuii AS-IS:** `VM.exec` `@tailrec` over immutable `ProgramState` (`VM.scala:228-256`, `ProgramState.scala:76-197`); `copy`-per-step, no mutable frame/pooling/`unsafe`.
- **Reference source (byte-cited):**
  - besu `evm/…/EVM.java:471` — `// Note: like runToHalt, this is performance-critical code. Benchmark before refactoring.` — besu's own hot-loop-is-sacred warning; the mutable `MessageFrame` is reused in-place across steps.
  - go-ethereum `core/vm/interpreter.go` — iterative `Run` loop mutating a reused `*ScopeContext` (stack/memory pooled); PC is `uint64`.
  - core-geth — same geth iterative mutable loop.
  - reth — revm handler loop over a mutable interpreter (external crate).
  - **All six vendored clients mutate an in-place frame; none uses immutable per-step state** (positive multi-client evidence — the AS-IS is the lone outlier, as `observations/evm.md` row "Interpreter loop" states: "recursion is nobody's choice").
- **Q1 — appropriate decision?** Yes. Treating it as a **benchmark-gated OPEN** (not "carry unchanged," not "must rewrite") is the correct, evidence-honest call: the source unanimously favors a mutable frame for throughput, but none of the six runs N isolated instances in one process (fukuii's R2 differentiator), so the isolation benefit is real and un-witnessed by the reference set.
- **Q2 — right thing to build?** Yes — build the bench first (erigon profile-driven discipline), then decide. Not NOTHING: the decision has a measured throughput cost. No better alternative surfaces — a mutable frame is single-threaded within one block execution, so no guard is needed if adopted.
- **Q3 — mechanism + blast radius correct?** Mechanism yes. **Blast radius the plan should make explicit:** a switch to a mutable frame ripples into (a) `ProgramState`/`Stack`/`Memory` API shape (every `copy`-returning mutator becomes an in-place mutate), (b) the `call`/`create` re-entry (a child frame must snapshot/restore for revert — the immutable loop gets "revert = keep old value" free; a mutable frame needs an explicit journal/undo, which is exactly what besu's `MessageFrame`/geth's snapshot do), and (c) the F11 second-gas-dimension counter (RX-L3-14) lives on the frame either way. The plan's §6 states the R2 benefit but not the revert-journal cost of the mutable alternative — fold that in so the bench compares like-for-like.
- **Q4:** n/a (OPEN is correct; blast-radius detail folded).
- **Verdict:** SHARPENS — fold into §6/§8: (1) the mutable-frame alternative requires an explicit revert journal (the immutable loop gets revert free); the bench must include that cost, not just per-step alloc; (2) record the all-six-clients-mutate positive evidence as the standard the bench is measured against.

- **fukuii AS-IS:** `EvmConfig.scala:150-151` `byteToOpCode: Map[Byte, OpCode]`; used at `VM.scala:231` (`config.byteToOpCode.get(byte)`).
- **Reference source (byte-cited):**

- **Q2 — right thing to build?** Yes. `IArray[OpCode]` is the faithful Scala-3 immutable analog of geth's `[256]*operation` / besu's `Operation[256]`, and its immutability satisfies R2 (RX-L3-13). No better alternative.
- **Q3 — mechanism + blast radius correct?** Yes. - **Q4:** n/a.
- **Verdict:** CONFIRMS (SHARPENS folded: §5/§6 — the sentinel is installed by **pre-filling all 256 slots** at build, besu `MainnetEVMs.java:205-207`, not a per-step null/`Option` check).

### RX-L3-03 · Build-time `validate` over the assembled table · Tier A · owner-layer L3
- **Plan claim / disposition:** §4 + §6 + §8 — **DEFAULT.** "Validated at init — **besu/geth both** check the assembled table at construction, the AS-IS `validate` gap." §6: "**Build-time `validate` invariant** … every opcode's `delta`/`alpha`/gas presence checked at construction; undefined-slot dispatch **fails loud**." §8 dispatch-invariant DoD: "the dense-table build-time `validate` passes."
- **fukuii AS-IS:** no build-time validation — the final artifact is an unvalidated `Map` (`clients/fukuii/evm.md` "no build-time `validate`").
- **Reference source (byte-cited):**
  - go-ethereum `core/vm/jump_table.go:76-95` — `func validate(jt JumpTable) JumpTable { for i, op := range jt { if op == nil { panic("op … is not set") }; if op.memorySize != nil && op.dynamicGas == nil { panic("op … has dynamic memory but not dynamic gas") } } }` — **called at the end of every fork constructor** (`newShanghaiInstructionSet` … `newOsakaInstructionSet` … `newAmsterdamInstructionSet` all `return validate(instructionSet)`, `:97-165`).
  - besu — **no `validate` pass exists.** `grep validate` over the besu `evm/` module returns nothing operating on the operation table; `OperationRegistry` has no validation method. besu's equivalent safety is the **pre-fill-with-`InvalidOperation`** construction (RX-L3-02) — there is no nil slot to check, so no validate is needed.
- **Q1 — appropriate decision?** Yes — a build-time invariant is the right DEFAULT; catching a malformed fork table at startup beats the first CALL to a broken opcode.
- **Q2 — right thing to build?** Yes. Adopt geth's `validate` **on top of** besu's pre-fill (they are complementary: pre-fill eliminates nulls; `validate` additionally asserts the memory/gas coupling invariant).
- **Q3 — mechanism + blast radius correct?** **No — two inaccuracies in the plan's understanding:** (a) **besu does NOT validate** — §4's "besu/geth both check the assembled table at construction" is wrong; only go-ethereum has a `validate` pass. besu instead pre-fills all 256 slots with `InvalidOperation`. (b) geth's `validate` checks **two things**: no-unset-op (nil panic) and the **`memorySize`-set-⟹-`dynamicGas`-set coupling** — it does **not** check "`delta`/`alpha`/gas presence" as §6 states (those are structural fields carried by the operation object, not what `validate` inspects).
- **Q4 — correct answer + why:** The build-time-`validate` DEFAULT is grounded in **go-ethereum only** (`jump_table.go:76`). Attribute it to geth; describe besu's alternative safety as the **pre-fill-with-`InvalidOperation`** dense construction (`MainnetEVMs.java:205-207`), not a validate pass. Specify what fukuii's `validate` should assert: (1) every slot is populated (guaranteed by the pre-fill, so this becomes a belt-and-suspenders assertion), (2) the memory/dynamic-gas coupling invariant geth checks — plus fukuii's own `delta`/`alpha` presence if desired (that is a fukuii addition, not "what geth does").
- **Verdict:** CORRECTS — §4: change "besu/geth both check the assembled table at construction" → "**go-ethereum** validates at construction (`jump_table.go:76`); **besu** instead pre-fills all 256 slots with `InvalidOperation` (`MainnetEVMs.java:205-207`) so no nil slot exists." §6: correct the "geth `validate(jt)`" description — it checks nil-op + `memorySize⟹dynamicGas`, and the `delta`/`alpha`/gas presence check is a fukuii-added assertion, not geth's.

### RX-L3-06 · Gas math on the JVM — `BigInt`, not Go `uint64`/`uint256` · Tier A · owner-layer L3
- **Plan claim / disposition:** §3 + §9 — the gas big-int arithmetic authority is **besu** (`gascalculator/GasCalculator.java` + subclasses): "128-bit stack words are where besu transfers and Go does not; read besu's `Gas`/`long` overflow handling." §9: "Gas math is JVM `BigInt` — the besu lens checks for Go `uint64`/`uint256` idioms that don't hold on the JVM."
- **fukuii AS-IS:** single-dimensional `BigInt`/`GasAmount` gas (`OpCode.scala:260-261`).
- **Reference source (byte-cited):**
  - besu `gascalculator/GasCalculator.java` — every method returns **`long`** (e.g. `long getVeryLowTierGasCost()`, `long memoryExpansionGasCost(…)`); besu uses `long` with **clamped arithmetic** (`Words.clampedAdd`/`clampedMultiply`/`clampedToInt`, imported in `OsakaGasCalculator.java:19-21`) to avoid overflow, not `BigInteger`.
  - go-ethereum `core/vm/gas.go` — `uint64` gas with explicit overflow checks (`math.SafeAdd`/`SafeMul`).
- **Q1 — appropriate decision?** Yes — the "gas is `BigInt` on the JVM, watch for Go `uint64` idioms" caution is correct and the besu lens is the right check.
- **Q2 — right thing to build?** Yes, with a **sharpening**: besu itself does **not** use `BigInteger` for gas — it uses **`long` + clamped/saturating arithmetic** (`Words.clampedAdd`). fukuii's `BigInt` gas is *safer* (no overflow possible) but *slower* (allocation per op). The plan cites besu as the `BigInt` authority, but besu is actually a `long`-clamped authority — the JVM lens should note this: fukuii's `BigInt` is a conscious correctness-over-throughput choice (like the immutable loop, RX-L3-01), not what besu does. If the immutable-loop bench (RX-L3-01) motivates a perf pass, gas-as-`long`-clamped is the besu-grounded option to weigh.
- **Q3 — mechanism + blast radius correct?** Mechanism yes; the overflow-handling detail (clamped `long` vs `BigInt`) is the load-bearing nuance to fold.
- **Q4:** n/a.
- **Verdict:** SHARPENS — §3/§9: besu's gas math is **`long` + clamped arithmetic** (`Words.clampedAdd`, `OsakaGasCalculator.java:19-21`), **not** `BigInteger`; fukuii's `BigInt` gas is the safer-but-heavier choice, a perf candidate to weigh under the RX-L3-01 bench, not a besu mirror.

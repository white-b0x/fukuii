## chain-facade

### RX-L7-01 · `chain` module `Blockchain` / `BlockchainReader` facade · Tier A · owner-layer L7
- **Plan claim / disposition:** STRUCTURAL spine. `chain` = read+write facade traits over storage (block/header/
  body/receipt/TD), relocated out of the old `domain` god-object ("SCC-breaking move #1"); a store facade only,
  no sync/execution/consensus logic; consumed by `sync` (L7) + `rpc` (L9), not by L2–L5; DAG `chain → storage,
  trie, domain`.
- **fukuii AS-IS:** `Blockchain*` was inside `domain`, forming a `domain ↔ Blockchain*` SCC (L1.md:206/376).
- **Reference source (byte-cited):**
  - besu `ethereum/core/.../chain/Blockchain.java:68,75` — read facade: `long getChainHeadBlockNumber()`,
    `Hash getChainHeadHash()` (+ header/body/receipt/TD getters above).
  - besu `.../chain/MutableBlockchain.java:41,59,77,89` — `interface MutableBlockchain extends Blockchain`
    adds the write half: `void appendBlock(...)`, `appendBlockWithoutIndexingTransactions(...)`,
    `storeBlock(...)`, `unsafeStoreHeader(BlockHeader, Difficulty)`. **The read/write split fukuii's
    `BlockchainReader`(read) / `Blockchain`(write) mirrors exactly.**
  - go-ethereum `core/blockchain.go` — the same store role (monolithic, not trait-split; besu is the split ref).
- **Q1 appropriate decision?** Yes. besu proves the read-facade / mutable-facade split as a first-class trait
  pair; relocating it above L2 (not inside `domain`) is what dissolves the SCC — the down-only edge to
  storage/trie/domain and up-only consumption by sync+rpc both hold.
- **Q2 what we should implement?** Yes — the read/write trait split is the right thing; it is not YAGNI (RPC needs
  read-only, sync needs write; besu separates them for exactly this).
- **Q3 understanding + blast radius correct?** Mechanism: yes. **Blast radius — one under-stated edge:** besu
  attaches the **reorg / block-added OBSERVER registration onto `Blockchain` itself** (`Blockchain.java:274
  observeBlockAdded`, `:308 observeChainReorg`). fukuii's plan deliberately does **not** — reorg-event authority
  and the `ChainNotification` ADT live at **L5** (`optimizations.md` L5 row; `requirements.md` R7). So the
  `chain` facade must stay a **pure store** and must **not** grow besu's observer hooks; the down-only consumers
  are L7 `sync` + L9 `rpc` (confirmed) — L9's resume-cursor reorg stream comes from L5's `grpc-seam`, never from
  `chain`. This conscious divergence-from-besu is the load-bearing blast-radius fact.
- **Q4 correct answer:** n/a (CONFIRMS decision; the blast-radius edge is a SHARPEN).
- **Verdict:** CONFIRMS (with SHARPENS below)
- **Plan edit:** §1 `chain` row — add a one-line blast-radius note: "besu couples block-added/reorg observers
  onto `Blockchain`; fukuii deliberately does not — reorg-event authority + `ChainNotification` are L5's, the
  `chain` facade stays a pure store (no observer registration)."

- **Plan claim / disposition:** OPTIONAL(role: server/archival/bootnode, F9). Default-off → on; DoS-bounded

    `maxTrieNodeLookups = 1024`, `maxTrieNodeTimeSpent = 5*time.Second`.

    `softResponseLimit` + a `hardLimit = req.Bytes*(1+stateLookupSlack)` (`:181`); **`GetTrieNodes`** caps on
    `bytes > req.Bytes || loads > maxTrieNodeLookups || time.Since(start) > maxTrieNodeTimeSpent` (`:525,531`);
    `GetByteCodes` caps on `maxCodeLookups` + `softResponseLimit`.

    2*1024*1024`, `:265,302,403,561 StopWatch.createStarted()` — size (2 MB, identical to geth) **+ wall-clock**.
    besu **also serves `GetBlockAccessLists`** (`:262-263`, `BlockAccessListsMessage`) — snap/2 BAL is wired on
    besu's server (see RX-L7-04).
- **Q1 appropriate decision?** Yes — a role-gated, default-off serving capability is the right shape (F9/R8/R9;
  fukuii-as-serving-workhorse GTM).
- **Q2 what we should implement?** Yes — the seam + role-gate now, DoS-bounded; not YAGNI (it is the GTM).
- **Q3 understanding + blast radius correct?** **SHARPEN:** the plan's DoD phrases the cap as one uniform

  message**: (a) account/storage ranges → 2 MB soft + `(1+0.1)` hardLimit, **no** lookup-count/wall-clock cap;
  (b) `GetTrieNodes` → bytes + `maxTrieNodeLookups=1024` + `maxTrieNodeTimeSpent=5s`; (c) `GetByteCodes` →
  `maxCodeLookups=1024` + 2 MB. The ≥1-item progress guarantee (RX-L7-02) is the account-range append-before-check.
  Blast radius: L6 (wire), L2 (scheme-dependent serve iterator).
- **Q4 correct answer:** the DoD serving-cap vector must be **per-message** with the exact geth constants above,
  not one generic triple.
- **Verdict:** SHARPENS
- **Plan edit:** §7 SNAP-serving row + §8 DoD bullet — replace "size + lookup + per-request-time" with the
  per-message cap table: account/storage-range = 2 MB soft + `req.Bytes*(1+stateLookupSlack=0.1)` hardLimit;
  `GetTrieNodes` = `req.Bytes` + `maxTrieNodeLookups=1024` + `maxTrieNodeTimeSpent=5s`; `GetByteCodes` =

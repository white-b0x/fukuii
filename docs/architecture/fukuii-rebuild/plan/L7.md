## 1. Scope & modules

**Two sbt modules in the L7 band** — `chain` (the block/blockchain store facade) and `sync` (the
acquisition tier); packages `com.chipprbots.fukuii.{chain,sync}.*`. DAG edges (down-only, per
`.local/docs/phase4/target-architecture.md`):

```
chain → storage, trie, domain
sync  → chain, network, consensus-api, execution, storage, trie
```

| Module | sbt id | Delivers |
|---|---|---|
| **chain** | `fukuii-chain` | The `Blockchain` / `BlockchainReader` **facade traits** over storage — block/header/body/receipt/total-difficulty read+write (relocated out of the old `domain` god-object, `L1.md §Layer-boundaries` "SCC-breaking move #1"). A store facade only: no sync/execution/consensus logic. Consumed by `sync` (this band) and `rpc` (L9); **not** by L2–L5 (execution/consensus reach state through `storage`/`trie`/`WorldStateProxy` directly, so the facade sits *above* them, at the L7 band). **besu couples block-added/reorg observers (`Blockchain.observeBlockAdded`/`observeChainReorg`) onto `Blockchain` itself; fukuii deliberately does not** — reorg-event authority + the `ChainNotification` ADT are L5's (L9's resume-cursor reorg stream comes from L5's `grpc-seam`, never from `chain`), so the `chain` facade stays a pure store with no observer registration. |
| **sync** | `fukuii-sync` | The acquisition tier below. |

Placing `chain` at the L7 band (not lower) is exactly why the old `domain ↔ Blockchain*` SCC dissolves:
the facade's only consumers are `sync` and `rpc`, both at/above L7, so a downward-only edge suffices and
no lower layer imports it (`L1.md:206/376`). `sync` depends on `chain` to persist/read blocks.

The `sync` module is the block/state acquisition tier: discover the heaviest chain (or take the CL's
head), download state fast, download the chain, heal, and hand a synced head to steady-state import.
Five strategies + shared plumbing:

- **SNAP sync** — snap/v1 range-proof state download (account/bytecode/storage ranges) + trie-node heal;
  the default/entry path. **SNAP serving** (F9) is a role-gated capability on the same wire.
- **Chain backfill** — headers/bodies/receipts forward from genesis, concurrent with SNAP state.
- **Regular sync** — steady-state fetch→validate→import→broadcast once caught up.
- **Fast sync** — legacy `GetNodeData` trie-node-by-hash download; retained only as an ETH68-only-network
  fallback + escape hatch.
- **Checkpoint sync** — bootstrap a fresh datadir from a trusted anchor.
- **Shared peer plumbing** — peer selection, rate tracking, pivot-header fetch, MESS branch-resolution
  hook (`Blacklist` now depends *down* into L6 `network`).

L7 is **not consensus** (`README.md` layer table: "no"). But it *invokes* consensus rules (MESS/ECBP-1100
node-local fork-choice, ETC PoW head selection) — those specific hooks are banksy-owned/forge-co-signed.

**Load-bearing ETC caveat** (SR best-practice synthesis): "the staged-pipeline and CL-driven-head clients
(erigon, reth, go-ethereum HEAD) **dropped PoW-from-genesis by construction**… **core-geth is the sole

### R8 role → sync-mode table (the explicit mapping, R8)

Sync is not one path — the mode is **selected per node role × network** (`requirements.md` R8). Each cell
composes from the seams below (per-family pivot selector × SNAP-serve gate × backfill depth × checkpoint):

| Node role | Sync mode | Serves SNAP? | History backfill |
|---|---|---|---|
| **Archival** (deep data for dApps) | **FULL** (or SNAP→FULL) + full history backfill | **yes** (default-on) | full, from genesis |
| **Tip / server** (tip-of-branch data server) | SNAP → regular; stays at tip | **yes** (default-on) | to pivot only |
| **Mining pool** (fukuii's #1 GTM, PoW) | SNAP → regular; stays at tip + **SNAP serving** for pool nodes | **yes** (default-on) | to pivot only |
| **RPC relay** (pruned public relay) | SNAP + checkpoint-pivot fast-bootstrap | optional | bounded |
| **Light / resource-light** | checkpoint-pivot; minimal state | no | none below anchor |
| **Bootnode** (F7/F8 infra — beyond the six R8 roles) | checkpoint-pivot + **SNAP serving** for joiners | **yes** (default-on) | as configured |
| **Validator** (PoS) | SNAP → regular; CL-driven by-hash pivot | optional | to pivot |

Every one of the six canonical R8 roles (archival · tip-server · **mining-pool** · pruned-relay ·
resource-light · validator — `requirements.md` R8, `L2.md` doctrine, matching L2's `MiningPool`
`StorageProfile`) is mapped; **bootnode** is an intentional *addition* for the F7/F8 serving-infra role,
not a substitution for a canonical role. The role selects the composition; the composition is built from
orthogonal seams, **not a longer `SyncMode` enum** (besu's enum actually *contracted* to `{FULL,SNAP}` —
"more sync approaches" is expressed as auto-bound seams).

## 4. besu structural mirror

The concrete besu shapes L7 follows (read alongside geth's Go for the snap bytes):

- **`PivotBlockSelector` + `DynamicPivotBlockSelector`** (`eth/.../sync/PivotBlockSelector.java`,
  `.../snapsync/DynamicPivotBlockSelector.java`) — the injected per-family seam. besu binds the selector
  once at controller build (`PivotSelectorFromPeers` for PoW, `PivotSelectorFromSafeBlock` for PoS/FCU).
  This is the target shape replacing old-fukuii's source-tag (§6). **For the frozen-ETC PoW-from-genesis
  arm specifically, the JVM cross-check is besu-etc's OWN `PivotBlockSelector`** (peer-driven, `FastSyncState`,
  no TTD) — vanilla besu removed ETC, so its `PivotSelectorFromPeers` serves only as the generic peer-pivot
  structural mirror. **`PivotSelectorFromSafeBlock` carries a
  dual-purpose CL-liveness guard** (`PivotSelectorFromSafeBlock.java:167-200`): (a) **fail-loud** when
  `effectiveThreshold = pivotBlockWindowValidity − millisSinceLastFcu/slotDuration <= 0` → "consensus client
  appears offline" (the shrink is **per-slot**, estimated missed slots since the last FCU), *and*
  (b) **pivot-reuse / anti-churn** — reuse the existing or cached-safe pivot while `head − pivot <
  effectiveThreshold` rather than re-pivoting on every head advance. Not just the offline-abort; the
  reference for the embedded-CL arm (R9/F9).
- **`DefaultSynchronizer`** (`eth/.../sync/DefaultSynchronizer.java`) — composes an initial-snap
  downloader + a permanent full-sync downloader. The clean composition L7's `SyncController` should
  express as supervised behaviors, not one 5,488-line file.
- **`SnapSyncDownloader` / `SnapWorldDownloadState` / `RequestDataStep` / `PersistDataStep`**
  (`snapsync/`) — the SNAP download-state + request/persist pipeline; the structural template for the L7
  SNAP feed actors (account/bytecode/storage/heal coordinators).
- **`SnapSyncChainDownloader` / `ChainDownloader`** — the chain-download-overlapping-state pattern
  (old-fukuii's `ChainDownloader` already cites "the Geth/Nethermind pattern"); keep it forward-from-genesis.
- **Checkpoint anchor** — besu's genesis-embedded `Checkpoint (number,hash,TD)` seeding `SyncState`,
  consumed automatically under SNAP. The reference for formalizing fukuii's checkpoint as data, not a mode.
- **SNAP serving caps** — besu bounds a serve response by **size + wall-clock** (geth uses `softResponseLimit`
  + `maxTrieNodeTimeSpent`); the reference for the DoS-bounded SNAP-serve role capability (§7, F9).

## 5. Scala 3 idiom targets (Pekko Typed — from line one)

L7 continues the L6 Typed invariants (`.agents/protocols/code-style/pekko-typed-api.md`); the actor
boundaries come from the SR nethermind-feed → channel-ownership mapping (`cross-cutting-themes.md`
Theme 1 — the actor-decomposition target), **decomposing the two monoliths structurally from the start**,
not a 1:1 port (R5/R6):

- **`SyncController` as a sealed `Command` ADT + named `Behavior` states**, never `Behavior[Any]`,
  never `context.become`. The runtime strategy transitions (`FallbackToSnapSync`, `RegularSyncStuck`,
  `SnapSyncFinalized`) stay message-driven events — but split across **supervised child feed behaviors**,
  not one monolith (§6.1).
- **Channel-ownership granularity — a supervised actor per feed** (account-range / bytecode / storage /
  trie-heal / chain-backfill), each owning exactly the state one geth goroutine would, plus a **selector
  actor publishing a mode-set** (the nethermind `MultiSyncModeSelector` shape). This is the
  OPTIONAL(enterprise/full) Phase-4 shape already *partially present* in the concurrent SNAP
  coordinators. **Per-context peer allocation** (nethermind `AllocationContexts`) partitions the shared
  pool so Snap and FastHeaders feeds don't starve each other. nethermind's `[Flags]` partition already
  reserves a distinct **`BlockAccessLists`** context (`AllocationContexts.cs:9-20`) — so when the snap/2
  versioned `Syncer` lands (§6.7), fukuii's partition should carry a BAL context so a v2 BAL feed doesn't
  starve v1 state feeds.
- **The pivot selector as an injected seam, `given`-bound per family** — besu's `PivotBlockSelector`
  becomes a `NetworkFamily`-typeclass-provided target selector (peers for PoW / FCU-safe-block for PoS),
  bound once at construction. **Inject through the typeclass, never `if (isPoSChain)` scattered through
  the loop** — old-fukuii's `CLPivotHint`/`isPoSChain` gate is a single boolean computed once
  (a good pattern to preserve), but the rebuild upgrades it to a proper injected selector.
- **Constructor-injected `ActorRef[Command]`** for every collaborator (peer client, storage, execution,
  consensus-api), never global lookup.
- **STOP-AND-ALERT death-watch** (`.agents/protocols/.../alert-wrapper-protocol.md`) — the
  `SnapSyncCriticalFailure` marker (crash while actively syncing = do not restart, in-flight session
  state is unsafe to resume) swapped to the benign `SnapSyncTerminated` at the finalize→backfill
  boundary. Preserve this narrow-window pattern.
- **Streams for chain download** — headers/bodies/receipts fetch as backpressured stream stages
  (flow-reviewed), consistent with the L6 Streams-Tcp direction; bounded-batch "not done, re-enter me"
  backpressure (the erigon `ErrLoopExhausted` / reth `ExecOutput{done:false}` discipline).
- **Typed test kit only** — `ActorTestKit`/`BehaviorTestKit` + stream test synchronization
  (`syncProbe`/`take(N)+Sink.seq`) for the feed graphs.

## 6. Improvements over old fukuii (AS-IS gaps this layer closes)

From [`clients/fukuii/sync.md`](../../../../.local/docs/research/clients/fukuii/sync.md):

1. **Split the 5,488-line `SNAPSyncController` (and 2,487-line `SyncController`).** Old-fukuii's
   `SNAPSyncController.scala` mixes phase orchestration, six retry/backoff subsystems, and inline
   incident documentation in one file (the largest in the subsystem). L7 decomposes into supervised feed
   actors (besu `SnapSyncDownloader` + nethermind `SyncFeed` shape) with a thin `SyncController` selector
   — the parallel-feed decomposition the SR names as the Phase-4 target, expressed structurally from the
   start rather than by accretion of point-fixes (61 commits / 90 days).
2. **Pivot selection: source-tag → injected seam.** Old-fukuii records *which* mechanism produced the
   pivot (`PivotSelectionSource`: `NetworkPivot`/`LocalPivot`/`CLDrivenPivot`,
   `SNAPSyncController.scala:4928-4941`) with a buffered `clPivotHint`. L7 makes it besu's **injected
   `PivotBlockSelector` seam bound per family** — the SR's "single most directly portable abstraction,"
   which old-fukuii approximates with a tag rather than an interface. The PoS arm gains besu's
   **CL-liveness guard** (fail loud when the CL appears offline) for the embedded-CL future (R9).
3. **Checkpoint: standalone archive → data anchor consumed by SNAP; interoperable ERA1 for archival.**
   Old-fukuii's `CheckpointArchive` (magic `0xC4C4C4C4`, CRC32) is a full-state-import container that
   **bypasses SNAP entirely** (`CheckpointImporter` marks all sync-done flags and SNAP never spawns) —
   effectively a 5th mode, and **bespoke / non-interoperable** with the ecosystem. The SR's guidance
   ("formalize the anchor as data, not a mode") is **not yet followed**. L7 reshapes the checkpoint into
   a besu-style trusted `(number,hash,TD)` anchor that **seeds** SNAP rather than replacing it — and if
   the archival full-import path is retained, it uses **ERA1** (geth/besu/nethermind/reth all consume it),
   not the bespoke container (§6.7).
4. **`Blacklist` now depends down into L6 `network`.** Old-fukuii declares `Blacklist` inside
   `blockchain/sync/` and lets `network` import it upward (`dependency-graph.md:50-51` back-edge). In the
   rebuild, **L6 owns `Blacklist`** (and its policy); L7 sync depends *down* on it — the cross-mode
   penalty-propagation shared cache (SNAP-blacklisted peer stays blacklisted into fast/regular) is
   preserved, just relocated.
5. **Uniform resumability + first-class unwind (state the unwind-order design choice).** Old-fukuii's
   resumability is ad hoc per strategy (`SnapSyncProgressStorage` + preserved account-range cursors +
   coarse `AppStateStorage` done-flags; "no uniform per-stage progress/unwind abstraction"). L7 adopts
   the erigon/reth discipline: a durable per-phase checkpoint integer + a first-class ordered unwind pass
   + bounded-batch backpressure — the *portable pieces*, not the staged pipeline. **The unwind-order
   design choice, stated explicitly:** reth uses **plain-reverse unwind + a centralized `on_stage_error`
   policy**; erigon uses a **hand-tuned `DefaultUnwindOrder`**. fukuii's **MPT-with-inline-roots means
   unwinds don't have erigon's cross-stage flat-state ordering hazards** — so **plain-reverse (reth) is
   the default choice** unless a specific cross-feed dependency forces a hand-tuned order; the decision is
   recorded, not left implicit.
6. **Config-surface the recovery levers.** Old-fukuii's manual-recovery escape hatches are JVM system
   properties (`-Dfukuii.reset-fast-sync-done`, `-Dfukuii.snap.clearDoneOnStart`,
   `-Dfukuii.seed-chain-weights`, read via `System.getProperty` inside `SyncController.start()`),
   invisible in HOCON. L7 makes them part of the config surface.
7. **SNAP serving as a first-class role capability + a versioned `Syncer`.** Old-fukuii covers serving
   *caps* in the DoD but not SNAP serving as a **role feature** (default-off → on for
   server/archival/bootnode). L7 makes it R8/R9-role-gated, DoS-bounded (geth `softResponseLimit` +

   — snap/2 is more wired across the ecosystem than the SR "not wired" snapshot captured; track-only stands.) The ecosystem-standard **ERA1** bulk-history format is the archival-import
   format (not the bespoke `CheckpointArchive`).

**Preserved as correct** (port, don't rewrite — these already match best-in-class, confirmed one-to-one
in §6.8): the concurrent SNAP account/bytecode/storage coordinators ("Geth-aligned: all 3 run
concurrently"), the forward-from-genesis `ChainDownloader` overlap, the single-phase trie-only heal

**proactive-pivot-roll within the serve window** (this IS the geth `120<128` / besu

chain-weight from the L2 local `chain-weight` CF, summing only L5-PoW-validated headers — never a wire

**HARDEN, do not preserve as-is** (§6.8 — the Workstream-A review confirms these backstops are
**environmentally load-bearing** for ETC's peer-scarce snap mainnet, an environment none of the three
references is validated against, so the INTENT stays; but the EXPRESSION is over-patched and gets
hardened): **heal-hold-on-stagnation** → keep the hold capability but (a) preserve content-addressed
healed progress across every pivot change (geth-style cheap re-pivot, `sync.go:604-606` — persisted nodes
carry over under any root), so hold-vs-roll governs only the *target*, never discards progress, and
(b) make the hold/roll decision first-principles (measured heal-rate vs serve-window-expiry-rate) rather
than a binary stagnation flag, paired with nethermind's sole-peer re-pivot-to-a-servable-root heuristic
so a pinned-but-unservable root re-pivots to what the scarce peers actually have instead of stalling; the
**SNAP↔Fast bounce + on-demand `StateNodeFetcher`** → keep the on-demand fetch as a legitimate
scarcity mechanism but make the force-complete **fail-loud** (alert: state incomplete, filling
on-demand), never the current *silent* mark-done that violates fukuii's own fail-loud discipline, and
keep pursuing background completeness; the **dormant-retry backoff** → keep (waiting for the few ETC peers
to re-index is a real recovery) but bound it and pair with the re-pivot-to-servable fallback; the
**restart-the-world stagnation watchdogs** → replace with nethermind's lighter counter → fall-asleep +
re-pivot model. See §6.8 for the byte-cited evidence and why the reference-client "simpler path" is a
regression on ETC.

### 6.8 Heal-backstop comparative verdict (Workstream A, 2026-07-14)

The earlier §6 preserved fukuii's heal backstops as "load-bearing operational hardening." A one-to-one
comparison against the actual geth/besu/nethermind heal machinery (byte-cited below, vendored trees read
2026-07-14) plus **operator production testimony** *confirms* that framing, with an important correction
to the **reason**. The snap wire is settled (§8); this is the heal *design* verdict the plan previously
hedged on — now decisive.

**Core finding:** fukuii's heal backstops are **environmentally load-bearing adaptations to ETC mainnet's
peer-scarce snap population (~1–5 snap-serving peers, high RTT) — an environment none of the three
references is validated against.** All three reference clients are tuned and tested on peer-*rich* ETH
mainnet (thousands of snap-serving peers), where heal converges within the serve window *because* serving
is fast and abundant. Their shared "simpler" model (re-pivot-and-re-heal, never hold) is simpler
**because they never face scarcity** — and **core-geth, the ETC authority, inherits geth's snap verbatim
and therefore has none of fukuii's scarcity backstops either.** So on peer-scarce ETC mainnet, adopting
the reference model wholesale would be a **regression, not a modernization** — the same trap §9 already
names for the PoW-from-genesis head, now applied to heal. **Operator testimony (2026-07-14):** the
re-pivot approach *was tried on ETC mainnet and kept failing* — "healing would happen but then there
would be issues due to the pivots… especially on ETC mainnet where there are very few snap peers" — which
is exactly why heal-hold-on-stagnation was introduced. A first-pass "REDESIGN to the reference model"
verdict was wrong on this point and is retracted here. The byte-cited reference mechanisms below are all
**validated on peer-rich mainnet**; each assumes the fast-heal precondition fukuii cannot count on:

- **The serve-window invariant (all three, first-principles):** the client moves the pivot forward while
  the *previous* pivot's state root is still inside the peer's serve window, so heal always has a servable
  root and converges without ever pinning. geth `2*64−8 = 120 < maxDiffLayers = 128`
  (`eth/downloader/beaconsync.go:306-318` vs `triedb/pathdb/config.go:69-70`); besu
  `DEFAULT_PIVOT_BLOCK_WINDOW_VALIDITY = 120` **explicitly derived** `= 128 − 8`
  (`SnapSyncConfiguration.java:22-28`, its own javadoc) vs server root-cache depth 128
  (`SnapServer.java:74`); nethermind `StateMaxDistanceFromHead = 128` vs `SnapServingMaxDepth = 128`
  (`SyncConfig.cs:85,76`). fukuii's proactive-pivot-roll (128-block window, margin ≈ 64) is the **same
  invariant** — KEEP it.
- **On re-pivot during heal, all three DISCARD the partial heal and restart against the fresh root — none
  holds:** geth cancels and rebuilds the healer/scheduler on every root change
  (`eth/downloader/statesync.go:57-73`, `eth/protocols/snap/sync.go:612-617`); besu's `reloadTrieHeal()`
  clears pending heal queues and re-enters against the new pivot (`SnapWorldDownloadState.java:271-287`,
  guard `reloadHealWhenNeeded` `SnapWorldStateDownloadProcess.java:465-472`); nethermind re-pivots each
  state-sync round (`StateSyncRunner.cs:73-116`). **besu even disables its generic stall watchdog for
  snap** (`markAsStalled` no-op, `SnapWorldDownloadState.java:160-163`) — recovery is unbounded re-enqueue
  + peer rotation, not stall-and-hold. **Discard-and-restart is cheap when serving is fast** (geth's
  already-persisted nodes carry over, `sync.go:604-606`, so only the delta re-heals); on a slow/scarce
  chain it is a **livelock risk** — every re-pivot throws away a heal walk that couldn't finish, and the
  next can't either. This is the failure the operator observed on ETC.
- **All three make heal-to-completion a HARD gate before full sync; none force-completes with incomplete
  state, and none has an on-demand import-time node fetch:** geth returns from `Sync` only when
  `Pending()==0` then commits the pivot (`sync.go:689` → `downloader.go:1019-1027`); besu completes
  `internalFuture` only after queue-drain (`SnapWorldDownloadState.java:206-230`); nethermind gates
  finalize on dependency-counted root-save + `VerifyPostSyncCleanUp` (`TreeSync.cs:60-62,746-764`). geth
  explicitly has **no** on-demand single-node fetch at execution time — completeness is front-loaded into
  heal. **All three therefore BLOCK INDEFINITELY on a chain they cannot heal** (bounded only by
  cancellation) — they choose correctness-and-block over fukuii's give-up-with-incomplete-state escape.
  fukuii's force-complete + on-demand `StateNodeFetcher` is the *only* design that chooses liveness
  (proceed, fill on-demand) over blocking-forever — defensible on a chain where "block until complete"
  can mean "never sync," but currently done *silently*, which is the real defect.

**The corrected reading:** the backstops are not a patch-cascade of mistakes — each addresses a real
ETC-scarcity failure mode the references never hit. fukuii's heal-hold pins the pivot so a heal walk that
can't finish within the ~28-min ETC serve window (`SNAPSyncController.scala:1382-1412`) still makes
monotonic forward progress against one fixed target, instead of the reference model's re-pivot livelock
that throws the walk away every window. The stagnation watchdogs, dormant-retry
(`SyncController.scala` recovery levers), and the SNAP↔Fast force-complete + on-demand `StateNodeFetcher`
(`checkSnapFastEscapeHatch`, `SyncController.scala:1270-1287`; `regular/StateNodeFetcher.scala:37-60`) are
each a scarcity recovery the peer-rich references never needed. But the **expression is over-patched**:
dueling magic constants (roll-window vs heal-hold), restart-the-world watchdogs, and a *silent*
force-complete that violates fukuii's own fail-loud discipline. The INTENT is load-bearing; the FORM gets
hardened. On the ETC-scarcity axis fukuii is **ahead of** core-geth (which carries geth's
peer-rich-assumption heal and nothing more).

**Per-component verdict (revised for the peer-scarcity reality):**

| fukuii backstop | references (all peer-rich) | Verdict |
|---|---|---|
| proactive-pivot-roll (128-window) | geth 120<128 · besu 120=128−8 · neth 128/128 | **KEEP + HARDEN** — derived, config-surfaced window knob (besu-style `serveWindow − buffer`), not a dueling magic number |
| single-phase trie-only heal | geth ✓ · neth ✓ · besu two-phase (Bonsai) | **KEEP** — correct for MPT-inline-roots (RX-L7-05) |
| durable `BfsQueue` heal queue | all in-mem | **KEEP** — durability aids resumability (issue #1167) |
| heal-hold-on-stagnation | none (all discard+restart, **assume fast heal**) | **KEEP (environmentally load-bearing) + HARDEN** — preserve content-addressed progress across pivot change (geth `sync.go:604-606`) so hold-vs-roll governs only the *target*; make hold/roll a measured heal-rate-vs-window-expiry decision, not a binary flag; add nethermind's sole-peer re-pivot-to-servable heuristic |
| dormant-retry (3–20 min) | none | **KEEP + HARDEN** — real recovery under scarcity (wait for few peers to re-index); bound it, pair with re-pivot-to-servable |
| stagnation watchdogs (restart-world) | geth none · besu disabled · neth counter/fall-asleep | **HARDEN → nethermind counter model**, not restart-the-world |
| SNAP↔Fast force-complete + on-demand fetch | all block-until-complete, no fetch | **HARDEN → fail-loud, not silent** — keep on-demand fetch as a legitimate scarcity liveness mechanism, but alert on incomplete state and keep pursuing background completeness; never silently mark done |

**Follow-up scarcity research (Workstream-A, dispatched 2026-07-14 → `docs/research/clients/topics/snap-heal-low-peers.md`).**
The verdict table above was drawn from a peer-*rich* reading; a second pass asked each reference directly:
*what does its snap heal do under low peers + slow serving?* geth and besu are in — and both **confirm the
references have no answer** and are, if anything, *weaker* than fukuii on this axis:

- **geth:** no scarcity-aware peer seeking, no static/frozen-pivot flag, no heal-timeout knob; the pivot
  rolls on blind block-distance with **no heal-rate feedback**; and the killer — a stale-root request
  returns empty → the peer is added to `statelessPeers` (`sync.go:2929-2931`) → on a 3-peer chain two or
  three empties collapse the usable set to **zero**, blocking until the next roll resets it: a genuine
  livelock. geth **never** commits partial state, so a chain it can't heal in time **does not sync at
  all.** "geth's robustness is emergent from mainnet peer abundance, not engineered into the heal
  algorithm." The one idea worth stealing is the deliberate `120<128` margin — which fukuii already has.
- **besu:** **won't even START untrusted snap below 5 confirming peers** (`PivotSelectorFromPeers.java:124-131`,
  `PivotBlockConfirmer.java:99,129`) — on a 1–3-peer ETC chain the *only* way in is a **trusted checkpoint
  pivot** (`PivotSyncActions.java:144-160`), which is exactly why fukuii ships `fukuii-checkpoint-service`;
  it **disconnects a slow peer after 5 timeouts** (`PeerReputation.java:41,78`), actively worsening
  scarcity; its 60 s re-pivot interval and 5 s request timeout are **hard-coded, not configurable**; and
  its own stall path `markAsStalled` is an unfinished `// TODO` (`SnapWorldDownloadState.java:160-163`).
  besu's heal can livelock on a slow link with **no keep-up detector, no give-up, and no operator alarm.**

So the corrected conclusion is stronger than "keep the intent": **the peer-rich references are the weaker
reference on the ETC-scarcity axis, and several of fukuii's backstops are capabilities they simply lack**
(a keep-up/heal-progress watchdog, a pivot-freeze-during-heal, a liveness give-up instead of block-forever,
RTT-tolerant peer handling). **nethermind (now in) closes the loop:** its **`StaticSnapPivot`**
(`SyncConfig.cs:57`) is a **mainstream client already shipping fukuii's heal-hold as a first-class config
knob** — it pins the pivot (`StateSyncPivot.cs:50-52`), disables the pivot-updater
(`StartingSyncPivotUpdater.cs:95`), relaxes peer gating (`MultiSyncModeSelector.cs:306,499`), and skips the
head-distance wait (`StateSyncRunner.cs:128`) so heal runs to completion against one unchanging root, never
orphaned by a re-pivot. The **scoping nuance**: nethermind's pin is scoped to a *pre-known checkpoint*
(`PivotNumber`+`PivotHash`, node idles after) — the checkpoint-bootstrap case, which maps onto fukuii's
checkpoint-service. fukuii's *live-PoW-head* heal-hold (freeze only while heal drains, then release) is a
**superset** nethermind does not offer. nethermind also confirms **content-addressed heal progress
survives a re-pivot** (`TreeSync.cs:493-532`) — the "preserve progress across pivot change" hardening above
is exactly what it does. Full evidence: [`snap-heal-low-peers.md`](../../../research/clients/topics/snap-heal-low-peers.md).

**Secondary diagnostic (still worth running):** measure fukuii's actual heal-walk node-count on ETC/Mordor.
If it is far larger than boundary-sized (references' heal is only the nodes missed *between* range
responses), part of the cost is an upstream range-download / inline-trie-build gap (L2 + coordinators,
route to `vault`) — a co-fix that would *reduce* how much the scarcity backstops must carry, though it does
not eliminate the scarcity problem itself.

**Decisive verdict:** KEEP proactive-pivot-roll + single-phase heal + `BfsQueue`; **KEEP the scarcity
backstops' intent (heal-hold, dormant-retry, liveness force-complete) — they target a regime the
references cannot handle — and HARDEN their form** (derived/config-surfaced window; content-addressed
progress preserved across pivot change; measured heal-rate-vs-window-expiry hold/roll decision; nethermind
counter-model watchdog not restart-the-world; **fail-loud** not silent force-complete; a genuine heal
keep-up/convergence signal none of the references has). Model the pin on nethermind's `StaticSnapPivot`
for the checkpoint-bootstrap case and build the live-head hold as fukuii's own superset; run the
heal-walk-size diagnostic to size the possible L2 co-fix. This closes the AS-IS gap the SR's one-line
"Healing" row left open: fukuii's single-phase heal *shape* matches geth (true), but its heal *backstops*
diverge — more machinery, because it targets a peer environment the SR's peer-rich references do not —
which the SR synthesis did not examine.

#### 6.8.1 Design decision — the per-network pivot-policy seam (resolves the verdict into architecture)

fukuii runs **both** families in one binary: ETH (abundant snap peers, CL-driven head) and ETC (scarce
snap peers, no CL). The heal-hold verdict above is therefore **not** a global mode choice — it is a
**per-network policy bound on the existing per-family pivot seam** (RX-L7-10; R1 "parameterized per
network via the injected selector, never `if(isPoSChain)` scattered"). Concretely, the injected
`PivotBlockSelector` gains a **pivot-policy axis** with (at least) three bindings, selected per network in
its `.conf`:

| Policy | Bound for | Behaviour | Base framework |
|---|---|---|---|
| **`RollingPivot`** | ETH/PoS (peer-rich, CL head) | traditional re-pivot-and-re-heal (the reference-client model) — correct where peers are abundant and the CL supplies the head | geth/besu/nethermind default path |
| **`StaticPivot`** | checkpoint bootstrap (any network) | pin to a **known** `(number,hash)`, sync state, then idle/hand to regular sync — maps directly onto `fukuii-checkpoint-service` | **port nethermind `StaticSnapPivot` verbatim** (production-grade, within nethermind's selector authority) |
| **`AdaptiveHold`** | ETC/PoW (scarce peers, no CL) | freeze the **live** head pivot *only while heal is draining*, then **release and roll forward** — fukuii's superset of `StaticPivot` (nethermind's pin never releases; it expects a CL / `ExitOnSynced`) | nethermind pin mechanics + fukuii's release-on-heal-drain + keep-up detector |

**Method (operator-endorsed): nethermind is the base, fukuii's practices are the delta.** Port
nethermind's `StaticSnapPivot` mechanics — pin (`StateSyncPivot.cs:50-52`), disable-updater
(`StartingSyncPivotUpdater.cs:95`), relax-peer-gating (`MultiSyncModeSelector.cs:306,499`), skip
head-distance wait (`StateSyncRunner.cs:128`) — as the shared foundation for both `StaticPivot` and
`AdaptiveHold`. Then evaluate each fukuii practice as a **delta on top**:

- **Adopt nethermind's** (fukuii's AS-IS already aligns, no rework): content-addressed heal progress
  preserved across a pivot change (`TreeSync.cs:493-532`), sole-peer re-pivot-to-servable
  (`SnapSyncFeed.cs:180-207`).
- **fukuii contributes (genuine superset — nethermind lacks it):** the **live-head hold** (freeze while
  heal drains, then release — `AdaptiveHold`, distinct from nethermind's never-releasing checkpoint pin);
  the **heal keep-up/convergence detector** that decides *when* to hold vs roll from measured
  heal-rate-vs-window-expiry (no reference has one); **fail-loud** force-complete; **snap-peer-scarcity
  visibility** (count snap-capable peers distinctly — all three conflate or ignore it).
- **Retire fukuii's over-patched form:** the binary stagnation flag (→ the measured hold/roll decision),
  restart-the-world watchdogs (→ nethermind's counter/fall-asleep model), silent force-complete (→
  fail-loud).

**"nethermind is the base" is per-concern, not whole-cloth** (full byte-level build spec:
[`snap-porting-reference.md`](../../../research/clients/topics/snap-porting-reference.md), a 4-agent
deep-dive of nethermind's SNAP with geth/besu cross-checks). nethermind is the base for the *control
machinery* (selector state-machine, feed/dispatcher + 8-way range partitioning, the dependency-counted
heal DAG + structural completeness proof, and the `StaticSnapPivot` pin) and its two **completeness
invariants are best-in-class — keep them** (bottom-up heal with the root saved last+flushed →
"root present ⇒ complete"; the `VerifyPostSyncCleanUp` corruption tripwire). **But on crash-resume
nethermind is the *weakest* reference — it persists no frontier** ("we can't actually resume snap sync on
restart", `ProgressTracker.cs:466`) and re-runs the whole range phase every restart; **besu is the
authority there** (a transactional per-dequeue frontier journal in dedicated column families) and
**fukuii's AS-IS already beats nethermind** (`SnapSyncProgressStorage` + preserved account-range cursors).
So: adopt besu's persistence model, keep/upgrade fukuii's cursor persistence, **do not inherit
nethermind's binary marker** — and keep WAL on for Phase-A range commits if a frontier is persisted (a
concrete port gotcha, since nethermind's `WriteFlags.DisableWAL` is safe only because it re-runs the
phase). Fill the gaps none of the three close: a besu-style **4 s serve wall-clock** (nethermind lacks
it), an explicit **≥1-item serve guard** (besu's is weak), the **heal keep-up detector**, and
**snap-peer-scarcity visibility** distinct from the eth-peer count.

**Also corrected by the deep-dive** (this vendored nethermind differs from older versions): there is **no
`SnapRanges` sync-mode** — ranges and heal both run under one `SyncMode.StateNodes`, sequenced *inside*
`StateSyncRunner.Run`; **long-range catch-up was removed** (don't port that edge); the **serve cap is 2 MB
in all three** clients (nethermind's adaptive 50 KB→**3 MB** figure is a *client request* size, not a
serve size — settling the "3 MB vs 512 KB" question: 512 KB = geth/besu client request, 3 MB = nethermind
client request, ≤2 MB = everyone's serve cap).

This is the decisive shape: **one SNAP engine, the pivot-policy swapped per network behind the existing
family seam** — `RollingPivot` for peer-rich ETH, `AdaptiveHold` for peer-scarce ETC, `StaticPivot` for
checkpoint bootstrap — with nethermind's production machinery as the control base, besu as the
persistence authority, and fukuii's live-head hold + keep-up detector + fail-loud + kept cursor
persistence as the evaluated deltas. It composes with the R8 role→mode table (§2) and the per-family
selector (§4) rather than adding a new top-level mode enum. **Consensus note:** the pivot policy is a sync
target, not a state-root rule (`SNAPSyncController.scala:1382-1412` "the healing pivot is a SYNC target,
not a consensus rule") — L7-owned, no forge/beacon gate, but the MESS/PoW-head hooks it sits beside
remain banksy/forge-owned (§9).

### 6.9 The bootstrap-source seam — flag-gated checkpoint distribution (incl. BitTorrent)

**Decision (2026-07-15):** torrent-based state distribution is **built at L7, not deferred.** The earlier
plan bucketed it under "ERA/frozen-segment bulk import → OPTIONAL(archival), NOT built" — but that misread
it as an archival convenience. It is actually **the single best available mitigation for the ETC
snap-peer-scarcity problem §6.8 documents**: on a chain with ~1–5 slow snap-serving peers, a node that can
fetch a verified state snapshot from *many BitTorrent seeders* is decoupled from the scarce peer set
entirely — the bootstrap that peer-driven SNAP struggles with becomes throughput-bound on seeders instead.
So it is pulled forward as a first-class, flag-gated capability.

**Shape — a `checkpointSource` axis, orthogonal to everything else.** Bootstrap-source answers *"where does
the initial state data come from,"* which is independent of the pivot-policy (§6.8.1, *how the pivot is
chosen/held*) and the SNAP-serve gate (§7, *whether we serve*). It composes with the R8 role→mode table's
`checkpoint` column (§2) rather than adding a mode. Config-selected per node:

```
fukuii.sync.checkpoint.source = anchor | http | torrent | db-snapshot   # default: anchor
fukuii.sync.checkpoint.torrent = <magnet-URI | infohash>               # when source = torrent
fukuii.sync.checkpoint.seedAfterImport = true                          # be a good network citizen
```

| Source | Transport | Payload | Reference |
|---|---|---|---|
| `TrustedAnchor` (**DEFAULT**) | chain-spec data | `(number,hash,TD)` seeds SNAP | besu genesis-embedded `Checkpoint` |
| `HttpArchive` | resumable HTTP-Range | **ERA1** segments | today's `CheckpointDownloader`, migrated off the bespoke `CheckpointArchive` to ERA1 |
| **`Torrent`** | **BitTorrent** (magnet/infohash) | **ERA1** segments | **erigon `OtterSync` `.seg`** — the torrent-distribution authority |
| `DbSnapshot` | file/HTTP | packaged DB snapshot | nethermind `Init.Snapshot` |

**Trust model — the transport never weakens trust.** A torrent delivers *bytes*, not authority. Every
fetched ERA1 segment is verified against (a) its own ERA1 **accumulator root**, (b) the **trusted
checkpoint anchor** `(number,hash,TD)` from the chain-spec, and (c) the reconstructed **final state root**,
**before** it seeds SNAP. Any mismatch → **hard reject + fail-loud** (poisoned-segment / malicious-seeder
defense), never a silent accept. This is besu's "a checkpoint is data-about-where-to-start, not an
algorithm" principle carried onto a peer-to-peer transport: BitTorrent is as trustworthy as HTTP here
because trust lives in the anchor + ERA1 roots, not the pipe. On torrent unavailability (no seeders) the
node **falls through to peer-driven SNAP** — the torrent is an accelerator, never a hard dependency.

**Why fukuii specifically:** (1) it is the structural answer to §6.8's few-snap-peer reality — the one
mitigation that doesn't depend on the peer population fukuii can't control; (2) **GTM** — mining pools
(fukuii's #1 market) and the fukuii project itself become snapshot *seeders*, turning the client's own
ecosystem into the bootstrap CDN; (3) enterprise single-binary nodes cold-start fast without waiting on
public peer availability. ERA1 (not the bespoke `CheckpointArchive`) is the payload so the segments are
interoperable with geth/besu/nethermind/reth torrents. **Layer boundary (reciprocates `L2.md` §"Layer
boundaries" + its era1 rows): L2 OWNS the ERA1 byte-canonical file format + accumulator + manifest** (the
committed `ColdStore` seam — identical bytes across nodes so torrent infohashes match); **L7 §6.9 owns only

## 9. Risks & consensus-critical flags

- **Not consensus, but MESS + PoW head are consensus-adjacent.** L7 changes no state root — but the
  **MESS/ECBP-1100 branch-resolution hook is banksy-owned/forge-cosigned** (node-local fork-choice
  preference, never a state-root rule), and the **PoW-from-genesis head election** is a core-geth-authority
  path forge cross-checks. Route those two hooks through the consensus-change protocol; the rest of L7 is
  ordinary layer work.
- **PoW-from-genesis regression is the standing trap.** The staged/CL-driven reference clients (erigon,
  reth, geth HEAD) *deleted* PoW-from-genesis by construction. Extracting their *resumability discipline*
  is correct; extracting their *head-selection model* would erase the only path a CL-less PoW node has to
  the heaviest chain. **Keep snap-state (geth wire) and PoW-head (core-geth) as separate concerns** — a
  reviewer who "modernizes" the head path toward geth-HEAD has introduced a regression.
- **Storage coupling caveat — do NOT adopt the staged *Execution* pipeline.** besu's SNAP⇒Bonsai and
  erigon's staged⇒flat-state show sync mode and storage format are a coupled pair. fukuii stores an
  **MPT with inline roots**, so erigon's staged Execution and its no-heal model are *structurally
  inapplicable* — the single-phase trie-only heal (flat slots inline) is correct here. Extract erigon/
  reth's *resumability + unwind ordering*, not their pipeline. This is also why **plain-reverse unwind
  (reth) is the default** — fukuii lacks erigon's cross-stage flat-state ordering hazards that force a
  hand-tuned `DefaultUnwindOrder`. Cross-ref `storage-persistence.md` before any sync↔storage co-change.
- **Stream-materialization / backpressure traps → flow.** The chain-download and feed graphs are exactly
  `flow`'s domain (a `Future` that never completes, silently-dropped elements, backpressure stalls). Every
  stream graph gets flow review + `pekko-resource-audit` (uncancelled timers, missing `watchWith`,
  materialization leaks) — the risk grows when the monolith is split into supervised feed actors.
- **The SNAP↔Fast bounce forces sync-done flags true even when state is incomplete** — a deliberate
  liveness-over-completeness trade in old-fukuii (`checkSnapFastEscapeHatch`). §6.8 keeps this *intent*
  (all three references block-forever on an unhealable chain, which on peer-scarce ETC can mean "never
  sync") but **hardens it to fail-loud**: the on-demand `StateNodeFetcher` (`GetTrieNodes`) must be
  provably wired AND the force-complete must **alert** on incomplete state and keep pursuing background
  completeness — never the current *silent* mark-done, which violates fukuii's own fail-loud discipline.
- **Pivot-freeze (heal-hold) is environmentally load-bearing, not premature-optimization — §6.8.** The
  128-block roll window, roll margin, and heal-hold-on-stagnation are empirical (dated ETC stalls, e.g.
  "ETC stalled 70+ min at 16.8M accounts") and target a **peer-scarce environment none of the three
  references handles** (geth livelocks via `statelessPeers`; besu won't start below 5 peers; nethermind's
  `StaticSnapPivot` is the same pin, checkpoint-scoped). **Keep the heal-hold; do NOT replace it with the
  peer-rich re-pivot model (tried on ETC, failed).** Harden the *form*: derive the window from the serve
  window (besu `120=128−8`), preserve content-addressed heal progress across any pivot change (geth
  `sync.go:604-606` / nethermind `TreeSync.cs:493-532`), make hold-vs-roll a measured heal-rate decision,
  and add a heal keep-up/convergence signal none of the references has. Named, documented config knobs,
  not buried magic numbers.
- **CL-liveness guard is a fail-loud requirement for the embedded-CL arm (R9).** The PoS pivot must not
  silently stall when the CL goes away — besu's shrinking `effectiveThreshold` → "consensus client appears
  offline" is the model; a silent stall here looks like a sync bug and hides an ops failure.
- **`core-geth is NOT SNAP-authoritative.** Its snap is inherited verbatim from geth — cite go-ethereum
  for every snap wire question; core-geth is authoritative only for the PoW head path + MESS.

### Layer boundaries

- **Owns:** the `chain` module — the `Blockchain` / `BlockchainReader` facade over storage (block/
  header/body/receipt/TD read+write), relocated out of the old `domain` god-object; and the `sync`
  module — the sync strategies (SNAP / chain-backfill / regular / fast / checkpoint), SNAP **serving**
  (role-gated), the per-family pivot-selection seam, the versioned `Syncer` seam, the shared
  peer-selection/rate-tracking plumbing (incl. per-context allocation), and the MESS branch-resolution
  hook wiring (the policy is banksy-owned; L7 wires it into the loop).
- **Depends down on:** `network` (peers, wire messages, the relocated `Blacklist` + its policy),
  `consensus-api` (fork dispatch, validation, `ProtocolSpec`), `execution` (block import/validate via the
  consensus adapter), `storage` (state/progress persistence), `trie` (MPT heal).
- **Does not own:** the wire protocol itself (L6 `network`), block execution / state transition (L4
  `execution` — L7 calls down into it), consensus rules (L5 — L7 references the engine, forge/beacon own
  the semantics), or the RocksDB storage layer (L2 — vault). The Engine-API driver that pushes the PoS
  head lives with `consensus-pos`; L7 consumes the head as a by-hash pivot.
- **Upward edges are compile errors** — nothing in `sync` may import `txpool`, `rpc`, or `node`, and the
  old `db/storage → blockchain.sync` back-edge (`FastSyncStateStorage`/`StateStorage` reaching up into
  sync) cannot re-form: storage is strictly downward.

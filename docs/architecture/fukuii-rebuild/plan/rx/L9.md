### RX-L9-02 · METHOD_NOT_ENABLED vs METHOD_NOT_FOUND (the SR-03 gap) · Tier B · owner-layer L9 `rpc`
- **Plan claim / disposition:** §2/§5/§6 DEFAULT — preserve **METHOD_NOT_ENABLED (known method, namespace off)** vs **METHOD_NOT_FOUND (unknown method)**; `july-fourth` "collapses both to `MethodNotFound` (`-32601`)" (`JsonRpcBaseController.scala:55-63`). - **fukuii `july-fourth`:** both collapsed to `-32601` — the SR-03 gap.
- **Reference source (byte-cited):**
  - besu `JsonRpcExecutor.java:166-186` `validateMethodAvailability` — `method == null` → **if `!RpcMethod.rpcMethodExists(name)` → METHOD_NOT_FOUND**; **else if `!rpcMethods.containsKey(name)` → METHOD_NOT_ENABLED**. The exact two-tier distinction.
  - besu `RpcErrorType.java` — both codes defined as distinct error types.
- **Q1 (appropriate?):** Yes — restoring the distinction is a real spec-compliance fix (a client can tell "turn on the `debug` namespace" from "no such method"); DEFAULT is right.
- **Q2 (what to implement?):** The `DispatchMiss` enum — correct.

Without that catalog, a disabled-namespace method is indistinguishable from an unknown one. The `enum DispatchMiss` alone does not supply it. Blast radius: local to `rpc` dispatch; feeds the JSON-RPC compliance suite (§8).
- **Verdict:** SHARPENS.
- **Plan edit (SHARPENS):** §5 — note the METHOD_NOT_ENABLED path requires an **all-known-methods catalog** (besu `RpcMethod` enum shape: every method fukuii could serve, independent of the per-instance enabled map); `DispatchMiss.NamespaceDisabled` is resolved by "name ∈ catalog ∧ name ∉ enabled", `MethodUnknown` by "name ∉ catalog".

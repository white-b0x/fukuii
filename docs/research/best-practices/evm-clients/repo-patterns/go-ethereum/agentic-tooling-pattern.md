## Summary

go-ethereum's own agentic tooling is the thinnest of any client audited in this series
(compare Nethermind's 9-file `.agents/rules/` stack + CI review bot, Erigon's
per-subsystem breadcrumbs + shipped MCP server + CI review bot, Reth's 549-line prose-rich
`AGENTS.md`). geth has exactly one root-level agent-context file — `AGENTS.md`, 102 lines —
and it is **checklist-only**: a numbered pre-commit sequence of shell commands with almost
no prose explanation of *why*, no architecture orientation section, no worked examples, no
PR-linked diffs, no commenting philosophy. Where Reth's `AGENTS.md` teaches an agent how
geth's maintainers *think*, go-ethereum's `AGENTS.md` only tells an agent what to *run*
before committing. This is not a gap to be alarmed by — it is the correct baseline to
validate against: **fukuii's own `AGENTS.md`/`CLAUDE.md` pair is already meaningfully
richer** than geth's (domain semantics for two consensus families, a working-discipline
section, a subagent roster, Spec Kit wiring, a protocol library) on every axis geth's file
covers, so this audit's main finding for that file is "already ahead," not "needs work."

The one place go-ethereum's tooling is genuinely interesting — arguably more interesting
than any single artifact in the Nethermind or Erigon audits — is
`.github/workflows/validate_pr.yml`, an 84-line CI gate that auto-detects and auto-closes
PRs whose titles match the pattern LLM-agent-authored spam contributions use
(`feat:`/`fix:`/`chore:` conventional-commit prefixes), with an explicit, publicly stated
rationale from the author: "I noticed that every single one of these PRs are low-quality
AI-slop." This is a **standalone-useful pattern independent of any "wait for outside
contributors" framing** — fukuii is public on GitHub under the `chippr-robotics` org and
currently has zero PR-title or PR-format validation of any kind, so this is directly
adoptable regardless of fukuii's current contributor volume. There is also a pointed irony
worth surfacing: the earlier, still-present half of that same workflow (the directory-
existence format checker) was itself, per its author's own commit message, "generated by
AI" — geth is using AI-authored CI tooling specifically to reject AI-generated PR spam.

### Structure

**Guidelines** (`AGENTS.md:3–6`) — two bullets, no elaboration:
- "Keep changes minimal and focused. Only modify code directly related to the task at
  hand. Do not refactor unrelated code, rename existing variables or functions for style,
  or bundle unrelated fixes into the same commit or PR." (line 5)
- "Do not add, remove, or update dependencies unless the task explicitly requires it."
  (line 6)

Both are negative constraints ("do not") rather than positive guidance — the file's
posture throughout is restrictive/gatekeeping rather than instructive, consistent with
being written by a maintainer managing unsolicited agent-authored contributions rather
than by someone onboarding an agent to build features.

**Pre-Commit Checklist** (`AGENTS.md:8–67`) — six numbered steps, every one of them an
exact shell command block with minimal prose:

| # | Section | Line(s) | Command | One-line purpose stated in file |
|---|---|---|---|---|
| 1 | Formatting | 12–19 | `gofmt -w <modified files>` then `goimports -w <modified files>` | (no purpose sentence — command only) |
| 2 | Build All Commands | 21–29 | `make all` | "Verify that all tools compile successfully" (line 23); "builds all executables under `cmd/`, including `keeper` which has special build requirements" (line 29) |
| 3 | Tests | 31–43 | `go run ./build/ci.go test -short` while iterating; `go run ./build/ci.go test` (no `-short`) before committing | Line 39: full run includes "the Ethereum execution-spec tests and all state/block test permutations" |
| 4 | Linting | 45–51 | `go run ./build/ci.go lint` | "runs additional style checks. Fix any issues before committing." (line 51) |
| 5 | Generated Code | 53–59 | `go run ./build/ci.go check_generate` | "Ensures that all generated files (e.g., `gen_*.go`) are up to date. If this fails, first install the required code generators by running `make devtools`, then run the appropriate `go generate` commands and include the updated files in your commit." (line 59) |
| 6 | Dependency Hygiene | 61–67 | `go run ./build/ci.go check_baddeps` | "Verifies that no forbidden dependencies have been introduced." (line 67) |

The `keeper` reference (line 29) is not stale boilerplate — verified against the actual
build tooling: `cmd/keeper` exists on disk, `build/ci.go` defines a `keeperTargets` slice
(`build/ci.go:81`) and a dedicated `doInstallKeeper` build path
(`build/ci.go:286–320`) that cross-compiles `keeper` binaries for multiple target
platforms into `keeper-<target>.tar.gz` archives — a materially different build shape
from the rest of `cmd/`, which is exactly the kind of "this one thing is special" detail a
checklist earns its keep by naming. `.github/CODEOWNERS:12` independently confirms
`cmd/keeper/` is a real, owned path (`@gballet`).

These six steps are not aspirational either — the actual CI workflow
(`.github/workflows/go.yml:34–37`) runs the identical commands as a hard gate on every PR
and push to `master`:
```yaml
- name: Run linters
  run: |
    go run build/ci.go lint
    go run build/ci.go check_generate
    go run build/ci.go check_baddeps
```
So `AGENTS.md`'s checklist is a **restatement of the real CI gate for a human/agent to
run locally before pushing**, not a separate or aspirational standard — an agent that
follows the checklist will not be surprised by CI.

**What to include in commits** (`AGENTS.md:69–71`) — the March 2 addition. One sentence:
"Do not commit binaries, whether they are produced by the main build or byproducts of
investigations." This is the file's only line that reads as a direct, specific reaction to
an observed agent failure mode rather than general good practice — the commit message
adding it says so explicitly (quoted above).

**Commit Message Format** (`AGENTS.md:73–86`):
```
<package(s)>: description
```
Three examples given verbatim (lines 82–84): `core/vm: fix stack overflow in PUSH
instruction`, `eth, rpc: make trace configs optional`, `cmd/geth: add new flag for sync
mode`. Rule: comma-separated package names for multi-area changes, description stays
concise (line 86).

**Pull Request Title Format** (`AGENTS.md:88–102`) — the file's final section, and the one
directly enforced by `validate_pr.yml` (below). Same shape as the commit-message format:
```
<list of modified paths>: description
```
Four examples (lines 97–100), including one showing the "top-level package paths" rule in
practice for a change to a specific nested module: `trie/archiver: streaming subtree
archival to fix OOM`. The closing sentence (line 102) states the scoping rule an agent
needs in order to not over-list paths: "Only mention the directories with functional
changes, interface changes that trickle all over the codebase should not generate an
exhaustive list."

### What the file does *not* contain

No architecture/component overview (contrast Reth's 9-crate table or Erigon's per-
subsystem breadcrumbs). No worked examples tied to real PRs (contrast Reth's six
PR-linked diffs). No testing-strategy taxonomy beyond "run this command." No commenting
philosophy, no anti-pattern list beyond "don't add binaries," no debugging tips, no
"finding where to contribute" guidance, no quick-reference cheat sheet at the end. The
file is, structurally, exactly one artifact: a pre-commit script written in prose instead
of as an actual script.

## validate_pr.yml — anti-AI-slop PR title/format validator

**File:** `.github/workflows/validate_pr.yml`, 84 lines, read in full. Triggers on
`pull_request: types: [opened, edited, synchronize]` (lines 3–5) — note `edited` is
included, so **editing an existing PR's title re-runs both gates**, not just the initial
open; a contributor cannot "sneak past" the check on open and rename the title
afterward without the check firing again.

### History (four commits, all by the same author)

| Commit | Date | Subject |
|---|---|---|
| `a9ac27558` | 2025-08-25 | `.github/workflows: naive PR format checker (#32480)` |
| `25d6596cd` | 2025-09-12 | `.github: remove redundant regexp check for heading dot (#32597)` |
| `7805e203f` | 2025-11-26 | `.github/workflows: validate that the directories exist (#33289)` |
| `b84097d22` | 2025-12-30 | `.github/workflows: preventively close PRs that seem AI-generated (#33414)` |

All four commits are authored by Guillaume Ballet — the same person who wrote
`AGENTS.md`, extending a roughly 4-month, single-maintainer campaign against low-quality
contributions from `a9ac27558` (Aug 2025) through `825436f04` (Mar 2026).

**Commit `a9ac27558` message, verbatim** (the original format checker, predates
`AGENTS.md` by six months): "Full disclosure: this has been generated by AI. The goal is
to have a quick check that the PR format is correct, before we merge it. This is to avoid
the periodical case when someone forgets to add a milestone or check the title matches
our preferred format." — **the format-validation script itself was authored by an AI
tool**, a detail the maintainer disclosed unprompted in the commit message.

**Commit `7805e203f` message, verbatim** (added the directory-existence check): "A new
pointless fad appeared recently where people just create a fairly low information tag at
the beginning of their github PR titles. Something like `feat` or other keywords. This
seems to originate from the angular community and to be used for automation scripts over
there. We do not use any of those scripts and if we did we would be using the github
labels, which offer strictly equivalent functionalities without wasting useful PR title
space. In order for these keywords to fail the validation, I am adding a check that these
directories listed indeed exist in the repository." This explains *why* the format gate
checks path existence rather than just regex shape — a bare `feat: add X` would otherwise
pass the loose `titleRegex` below (since `feat` matches `[\w\s,{}/.]+`) unless `feat` is
also rejected for not being a real directory in the repo.

**Commit `b84097d22` message, verbatim** (added the spam-title auto-close step, five
weeks after the directory check): "This is a new step in my crusade against the braindead
fad of starting PR titles with a word that is completely redundant with github labels,
thus wasting prime first-line real-estate for something that isn't necessary. I noticed
that every single one of these PRs are low-quality AI-slop, so I think there is a strong
case to be made for these PRs to be auto-closed. A message is added before closing the
PR, redirecting to our contribution guidelines, so I expect quality first-time
contributors to read them and reopen the PR. In the case of spam PRs, the author is
unlikely to revisit a given PR, and so auto-closing might have a positive impact. That's
an experiment worth trying, imo." This is the single clearest first-person statement of
motivation found in any client's agentic-tooling artifacts across this whole audit series
— an explicit acknowledgment that the trigger pattern (`feat:`/`fix:`/`chore:` prefixes)
correlates with AI-generated spam specifically, and an explicit design choice (auto-close
with a redirect message, betting that legitimate contributors read and reopen while spam
authors don't come back).

### Step 1 — "Check for Spam PR" (lines 11–48), quoted verbatim

```javascript
const prTitle = context.payload.pull_request.title;
const spamRegex = /^(feat|chore|fix)(\(.*\))?\s*:/i;

if (spamRegex.test(prTitle)) {
  // Leave a comment explaining why
  await github.rest.issues.createComment({
    owner: context.repo.owner,
    repo: context.repo.repo,
    issue_number: context.payload.pull_request.number,
    body: `## PR Closed as Spam

This PR was automatically closed because the title format \`feat:\`, \`fix:\`, or \`chore:\` is commonly associated with spam contributions.

If this is a legitimate contribution, please:
1. Review our contribution guidelines
2. Use the correct PR title format: \`directory, ...: description\`
3. Open a new PR with the proper title format

Thank you for your understanding.`
  });

  // Close the PR
  await github.rest.pulls.update({
    owner: context.repo.owner,
    repo: context.repo.repo,
    pull_number: context.payload.pull_request.number,
    state: 'closed'
  });

  core.setFailed('PR closed as spam due to suspicious title format');
  return;
}

console.log('✅ PR passed spam check');
```

**Exact behavior:**
- The regex `/^(feat|chore|fix)(\(.*\))?\s*:/i` matches a title that starts with
  `feat`, `chore`, or `fix` (case-insensitive), optionally followed by a parenthesized
  scope (e.g. `feat(rpc):`), optional whitespace, then a colon. This is the Conventional
  Commits / Angular-style prefix convention geth explicitly does not use (per the
  `7805e203f` commit message above).
- On a match: posts a PR comment (a level-2 Markdown heading "PR Closed as Spam", the
  reason, a 3-step remediation list pointing at the contribution guidelines and the
  correct title format, and a closing thank-you line) via
  `github.rest.issues.createComment`.
- Then **closes the PR immediately** via `github.rest.pulls.update({ state: 'closed' })`
  — no human review step, no maintainer approval required, no delay. This runs on every
  `opened`/`edited`/`synchronize` event, so it fires the instant a matching title is
  submitted.
- Calls `core.setFailed(...)` and `return`s — the job step (and therefore the overall
  `validate-pr` job) reports as failed, and **execution stops before the second step
  ("Checkout repository") or the format-check step ever run** for that invocation. A
  spam-matching title never reaches the directory-existence check at all.
- On no match: logs `✅ PR passed spam check` and falls through to the next step.

### Step 2 — "Check PR Title Format" (lines 53–83), quoted verbatim

```javascript
const fs = require('fs');
const path = require('path');
const prTitle = context.payload.pull_request.title;
const titleRegex = /^([\w\s,{}/.]+): .+/;

if (!titleRegex.test(prTitle)) {
  core.setFailed(`PR title "${prTitle}" does not match required format: directory, ...: description`);
  return;
}

const match = prTitle.match(titleRegex);
const dirPart = match[1];
const directories = dirPart.split(',').map(d => d.trim());
const missingDirs = [];
for (const dir of directories) {
  const fullPath = path.join(process.env.GITHUB_WORKSPACE, dir);
  if (!fs.existsSync(fullPath)) {
    missingDirs.push(dir);
  }
}

if (missingDirs.length > 0) {
  core.setFailed(`The following directories in the PR title do not exist: ${missingDirs.join(', ')}`);
  return;
}

console.log('✅ PR title format is valid');
```

**Exact behavior:**
- Runs only after a "Checkout repository" step (`actions/checkout@v4`, line 51) — the
  repository must be present on disk at `GITHUB_WORKSPACE` for the directory-existence
  check to have anything to stat.
- `titleRegex = /^([\w\s,{}/.]+): .+/` requires the title to start with one or more
  characters from the set `[word chars, whitespace, comma, brace, slash, dot]`, followed
  by a literal `": "`, followed by anything (the description). If the title doesn't match
  at all (e.g. no colon present), `core.setFailed` fires immediately with a message
  naming the exact offending title and the expected shape (`directory, ...: description`).
- If it does match, the captured group 1 (everything before `": "`) is split on commas
  and each segment is `.trim()`-ed — this is what turns `core/vm, eth: description` into
  `["core/vm", "eth"]`.
- **Directory-existence check, per segment:** for each trimmed path candidate, it builds
  `path.join(process.env.GITHUB_WORKSPACE, dir)` and calls `fs.existsSync(fullPath)`. Any
  segment that doesn't resolve to a real path in the checked-out tree is collected into
  `missingDirs`.
- If `missingDirs` is non-empty, `core.setFailed` fires listing every missing directory by
  name, comma-joined. This is the check that specifically defeats a bare `feat: ...` title
  that survived Step 1 by using a different disallowed word (or defeats any title using a
  path that simply doesn't exist in the repo, catching typos and made-up package names
  alike) — `feat` is not a directory in go-ethereum's tree, so `feat: add X` would fail
  here even if it had somehow dodged the spam regex.
- On success: logs `✅ PR title format is valid` and the job passes.

### The irony, stated plainly

Step 2's exact logic (the `titleRegex` + `fs.existsSync` loop) is, per the author's own
disclosure, AI-generated (`a9ac27558`). Step 1 (the spam-title auto-close, added five
months later) exists specifically to reject PRs whose titles look AI-generated. geth is
running AI-authored code as a gate against AI-authored spam — worth keeping in mind as a
data point about the current state of the art: an AI tool can write a perfectly adequate,
narrowly-scoped regex validator, while a *different* category of AI-driven contribution
(unsolicited, low-effort, conventional-commit-titled PRs) is exactly what that validator's
sibling step exists to reject. The two are not in tension — a scoped, human-directed use
of AI to write a 30-line CI script is a different act than an autonomous agent opening a
low-quality PR unprompted — but the juxtaposition inside one 84-line file is notable.
